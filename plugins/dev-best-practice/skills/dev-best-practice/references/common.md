# 언어를 가리지 않는 배치 판정

패키지 안의 모듈을 어떻게 묶고 이름 짓는지.

## 1. 폴더는 관심사나 도메인에만 만든다

폴더를 만들 근거는 다음뿐이다.

- **한 관심사에 파일이 여럿** — 출력 형식을 다루는 파일이 넷이면 `output/`
- **도메인 경계** — `installation/`, `publishing/`
- **가시성** — `_internal/`, `deprecated/`

**층위 이름 폴더를 만들지 않는다.** `convert/`, `commands/`, `utils/`, `services/`, `handlers/`가 여기 해당한다. 파일이 늘어 답답할 때 층위로 자르면 정리된 것처럼 보이지만, 실제로는 한 기능을 고칠 때 열어야 하는 폴더 수만 늘어난다. "변환하는 것끼리", "검사하는 것끼리"는 폴더를 만들 근거가 아니다.

근거: 널리 쓰이는 Python 패키지 넷을 열어 확인한 결과(2026-07-30), 폴더 이름이 전부 명사 도메인이거나 관심사였고 층위 이름을 쓴 것은 없었다.

| 패키지 | 구조 | 폴더의 기준 |
|---|---|---|
| pydantic | 평평 — `main.py`, `fields.py`, `config.py`, `json_schema.py` | `_internal/`, `deprecated/`, `experimental/` |
| bs4 | 평평 — `element.py`, `css.py`, `formatter.py`, `filter.py` | `builder/` (파서 구현이 여럿) |
| httpie | 평평한 파일 15개 + 폴더 6개 | `cli/`, `output/`, `plugins/`, `manager/` |
| poetry | 도메인 폴더 18개 | `installation/`, `packages/`, `repositories/`, `publishing/` |

## 2. 규모가 폴더 수를 정한다

| 파일 수 | 배치 |
|---|---|
| 20개까지 | 평평하게 둔다. 폴더는 0개나 1개 |
| 20~40개 | 평평한 파일 + 관심사 폴더 3~6개 |
| 40~100개 | 관심사 폴더를 늘리되, 폴더 하나에 8개 이상 들어갈 때만 만든다 |
| 100개 이상 | 도메인 폴더 |

기준은 폴더 개수가 아니라 **폴더 하나에 몇 개가 들어가는가**이다. 파일 25개짜리에 폴더 4개를 만들면 폴더마다 평균 6개가 들어간다. import 경로만 길어지고 파일을 찾는 비용은 줄지 않는다. `junegunn/fzf`의 `src/`는 파일 47개에 폴더 4개로 폴더마다 평균 12개다(2026-09-02 확인).

**구간 경계에서는 무엇을 세었는지가 결론을 바꾼다.** 생성된 파일이나 소스 옆 테스트를 포함하는지에 따라 구간이 갈리면, 무엇을 넣고 뺐는지 밝히고 두 경우의 결론을 함께 적는다.

**Go에서는 폴더를 만들기 시작하는 파일 수가 더 크다.** 디렉토리가 곧 패키지 경계라서 폴더를 만들면 import 경로와 공개 범위가 함께 바뀐다. 폴더를 만드는 비용이 다른 언어보다 크므로 더 오래 평평하게 둔다. `spf13/cobra`는 파일 34개를 폴더 없이 두고, `junegunn/fzf`의 `src/`는 파일 47개에 폴더 4개다(2026-09-02 확인).

## 3. 파일 이름은 대상을 가리킨다

동작이 아니라 **다루는 것**의 이름을 쓴다. `sessions.py`, `downloads.py`, `element.py`, `packages.py`.

| 피할 이름 | 왜 | 고침 |
|---|---|---|
| `utils.py`, `helpers.go`, `common.ts` 같은 **파일** | 무엇이든 들어가서 결국 아무도 읽지 않는다 | 안에 든 것을 대상별 파일로 나눈다 |
| `manager`, `handler`, `service` | 무엇을 관리하는지가 이름에 없다 | `sessions`, `downloads` |
| 읽기 모듈의 `article` | 대상 이름이지만 그 모듈이 무엇을 하는지 안 보인다 | 산출물 이름으로 — `post` |
| 같은 이름이 두 경로에(`model.py`와 `x/model.py`) | import 문에서 어느 쪽인지 구분되지 않는다 | 한쪽을 산출물 이름으로 — `result.py` |

**한 파일이 두 방향의 변환을 갖지 않는다.** A를 B로 바꾸는 코드와 B를 A로 바꾸는 코드를 한 파일에 넣으면 이름이 자료 형식(`viewer_html.py`)이 되고 무엇을 무엇으로 바꾸는지가 이름에서 사라진다. 방향마다 파일을 나누고 이름에 방향을 넣는다.

**`util/` 폴더는 파일과 다르게 판정한다.** 널리 쓰이는 저장소에 실제로 있고, 그 안이 다시 대상별 파일로 나뉘어 있으면 문제가 없다(2026-09-02 확인).

| 대상 | 내부 |
|---|---|
| `tokio/src/util/` | 파일 22개가 전부 대상 이름 — `linked_list.rs`, `try_lock.rs`, `atomic_cell.rs` |
| `hugo/common/` | 폴더 28개가 전부 대상 이름 — `hashing`, `paths`, `text`, `urls`, `version` |
| `fzf/src/util/` | 대상 이름 파일들 사이에 `util.go`가 하나 섞여 있다 |

판정 기준은 이름 자체가 아니라 **그 안에서 다시 대상별로 나뉘는가**이다. `util/` 폴더 안에 다시 `util.go`를 만드는 것이 실제 문제다.

## 4. 기능별로 자를지 층위별로 자를지

| | 기능별 (vertical slice) | 층위별 (layered) |
|---|---|---|
| 묶는 기준 | 기능 하나가 자기 요청과 검증과 로직과 저장을 다 가진다 | 층마다 폴더를 만든다 |
| 이득 | 기능 변경이 한 폴더 안에서 끝난다 | 층별로 교체하고 테스트한다 |
| 손해 | 기능 사이 공유 코드가 되풀이된다 | 기능 하나가 여러 폴더에 나뉜다 |
| 맞는 곳 | 기능끼리 공유가 적은 웹 API | 층 교체가 잦은 시스템 |

**판정 질문: 기능들이 무엇을 공유하는가.** 도메인 모델 하나를 전부가 공유하면 기능별로 잘라도 그 모델이 기능 폴더 밖에 남아 결국 둘을 섞은 형태가 된다. 그럴 때는 처음부터 도메인으로 나누고 그 안에서 층위로 나눈다.

"요즘 vertical slice가 낫다더라"로 고르지 않는다. 공유 코드의 크기를 먼저 확인한다.

출처: <https://milanjovanovic.tech/blog/vertical-slice-architecture>, <https://antondevtips.com/blog/n-layered-vs-clean-vs-vertical-slice-architecture>

## 5. 재편할 때

파일을 옮기는 것은 동작이 바뀌지 않는 변경이다.

- 기존 테스트가 변경 전과 후에 모두 통과하는지 작은 단위로 나누어 확인한다.
- 이름 변경과 기능 추가를 한 커밋에 섞지 않는다. diff에서 새 코드와 파일 이동이 뒤섞여 검토가 되지 않는다.
- 옮기기 전에 import 관계를 확인해 순환 참조가 생길 곳을 찾는다.

## 6. 저장소가 이미 정한 규약이 이 판정보다 앞선다

배치와 이름을 이미 정해 둔 것이 저장소에 있으면 그것을 따른다. 코드만 이 판정에 맞추면 문서와 코드가 서로 다른 이름을 쓰게 되고, 그 비용이 이름이 규칙과 다른 비용보다 크다.

무엇이 규약인가. 위가 아래보다 앞선다.

| 순위 | 무엇 | 어디서 확인하나 |
|---|---|---|
| 1 | 바꿀 수 없는 프레임워크 규정 | Next.js `app/`의 라우팅 폴더와 `route.ts` 같은 파일 이름. 판정 대상이 아니다 |
| 2 | 저장소 문서가 적은 배치 규칙 | `README.md`, `CONTRIBUTING.md`, `docs/`, `CLAUDE.md`의 구조를 다루는 절 |
| 3 | 이 참조 파일의 판정 | |

**설정 파일이 정한 경로는 도구가 아니라 저장소가 고른 것이다.** `components.json`의 `aliases`와 `tsconfig.json`의 `paths`는 값을 바꾸면 도구가 다른 경로에 파일을 넣는다. "도구가 고정해서 어쩔 수 없다"는 이 경우에 성립하지 않는다.

그 경로를 어떻게 볼지는 참조 파일이 이미 판정했는지로 갈린다.

- **참조 파일이 그 배치를 판정했으면 그 판정을 따른다.** `react.md` 판정 2가 `shadcn init`이 만드는 기본 경로를 그대로 두라고 정하는 것이 그 경우다.
- **기본값에서 바꿔 둔 배치는 2순위로 본다.** 왜 바꿨는지가 문서에 있으면 따르고, 없으면 아래 처분을 적용한다.

규약을 찾았으면 **그 규약에 이유가 적혀 있는지**로 처분이 갈린다.

- **이유가 있으면** 그대로 따르고 어긋난 항목으로 올리지 않는다. 무엇을 근거로 넘어갔는지 문서의 위치와 함께 한 줄로 적는다.
- **이름만 정해져 있고 이유가 없으면** 어긋난 항목이 아니라 규약 수정 제안으로 낸다. 제안에는 어느 판정과 어긋나는지, 문서의 어느 부분을 함께 고쳐야 하는지, 코드 몇 개가 따라 바뀌는지를 적는다. 고칠 때는 문서를 먼저 고치고 코드를 그 다음에 고친다.

**이유가 사실인지 확인한다.** 문서가 적은 이유가 실제와 다르면 이유가 없는 것으로 본다. 제안에는 배치를 바꾸는 것과 문서의 이유를 사실에 맞게 고치는 것을 함께 적어 사용자가 고르게 한다.

규약이 실제 코드와 다르면 규약이 낡은 것이다. 어느 쪽에 맞출지 사용자에게 묻는다.
