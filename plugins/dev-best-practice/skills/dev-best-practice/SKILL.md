# dev-best-practice

소스 트리 배치에 대한 개인 기준. 두 가지 방식으로 쓴다.

## 경계

- **판정은 `references/`에 적힌 것만 쓴다.** 거기 없는 상황은 기준이 없다고 말한다.
- **얼마나 강하게 적용할지는 이 세션에서 사용자와 정한다.** 새로 쓰는 코드에만 적용할지, 기존 코드까지 고칠지, 이번에는 넘어갈지는 프로젝트마다 다르다. 기준 자체가 그것을 정하지 않는다.
- **어긋난 항목을 전부 나열한 뒤에 무엇을 고칠지 묻는다.** 사용자가 고른 것만 고친다.

## 참조 파일

| 파일 | 언제 읽나 | 담는 것 |
|---|---|---|
| `references/common.md` | 폴더를 만들거나 파일 이름을 정하기 전. 구조 점검을 시작할 때 | 언어와 프레임워크를 가리지 않는 배치 판정 |
| `references/react.md` | 위에 더해, 대상이 React나 Next.js 저장소일 때 | 슬라이스와 세그먼트 배치, 배럴 파일 판정, `features`의 두 뜻, Next.js 배치 도구 |

## 1. 코딩 중 참조

참조 파일의 판정을 적용한다. 기준과 어긋나는 코드를 이미 쓰고 있으면 어긋난 지점을 사용자에게 말한다.

## 2. 구조 점검

사용자가 "구조 점검해줘", "이 프로젝트 기준에 맞나 봐줘"라고 하면 다음 순서로 한다.

1. 참조 파일을 읽는다.
2. 현재 저장소의 디렉토리 구조와 파일 목록을 확인한다. 소스 디렉토리의 파일 수, 폴더 이름, 파일 이름을 센다. 무엇을 세지 않는지는 아래 Edge Cases에 있다.
3. 기준과 어긋나는 항목을 찾는다. 항목마다 **파일 또는 폴더 경로**, **어느 판정과 어긋나는지**, **무엇으로 고칠 수 있는지**를 적는다.
4. 어긋난 항목을 전부 나열한 뒤 사용자에게 무엇을 고칠지 묻는다.
5. 사용자가 고른 것만 고친다.

어긋난 항목이 없으면 없다고 말한다.

### 점검 결과 형식

이 형식으로 낸다.

```markdown
## 구조 점검 — <저장소 이름>

**확인한 범위**: <디렉토리 경로>, 파일 <N>개, 폴더 <M>개

### 어긋난 항목

1. `<파일 또는 폴더 경로>` — <어느 판정과 어긋나는지>
   - 지금: <현재 상태>
   - 고침: <무엇으로 바꾸나>

2. `<경로>` — ...

### 확인했고 문제없는 것

- <판정 이름>: <왜 문제없는지 한 줄>

### 정할 것

고칠 항목의 번호를 알려주세요.
```

번호는 어긋난 항목이 여러 묶음이어도 다시 시작하지 않고 이어서 매긴다.

## Edge Cases

| 상황 | 어떻게 하나 |
|---|---|
| 벤더와 생성 코드가 섞여 있다 | `node_modules/`, `.venv/`, `vendor/`, `dist/`, `build/`, 생성된 타입 파일과 마이그레이션은 세지 않는다. 무엇을 뺐는지 점검 결과의 "확인한 범위"에 적는다 |
| 패키지가 여럿이다 | 판정은 패키지 하나에 걸린다. 패키지마다 따로 세고 따로 보고한다 |
| 소스 디렉토리가 불분명하다 | `src/`가 없으면 무엇을 소스로 볼지 사용자에게 먼저 확인한다. 짐작해서 세지 않는다 |
