# dev-best-practice

소스 트리 배치에 대한 개인 기준. 두 가지 방식으로 쓴다.

## 경계

- **판정은 `references/`에 적힌 것만 쓴다.** 거기 없는 상황은 기준이 없다고 말한다.
- **얼마나 강하게 적용할지는 이 세션에서 사용자와 정한다.** 새로 쓰는 코드에만 적용할지, 기존 코드까지 고칠지, 이번에는 넘어갈지는 프로젝트마다 다르다. 기준 자체가 그것을 정하지 않는다.
- **어긋난 항목을 전부 나열한 뒤에 무엇을 고칠지 묻는다.** 사용자가 고른 것만 고친다.

## 참조 파일

| 파일 | 언제 읽나 | 담는 것 |
|---|---|---|
| `references/common.md` | 폴더를 만들거나 파일 이름을 정하기 전. 구조 점검을 시작할 때 | 언어와 프레임워크를 가리지 않는 배치 판정 |
| `references/react.md` | 위에 더해, 대상이 React나 Next.js 저장소일 때 | 기능 폴더와 세그먼트 배치, 최상위 공용 폴더, 배럴 파일 판정, 경계를 강제하는 린트 설정, Next.js 배치 도구, 파일 이름 |

## 1. 코딩 중 참조

참조 파일의 판정을 적용한다. 기준과 어긋나는 코드를 이미 쓰고 있으면 어긋난 지점을 사용자에게 말한다.

## 2. 구조 점검

사용자가 "구조 점검해줘", "이 프로젝트 기준에 맞나 봐줘"라고 하면 다음 순서로 한다.

1. 참조 파일을 읽는다.
2. 저장소가 이미 정한 규약을 모은다. 도구 설정 파일과 저장소 문서(`README.md`, `CONTRIBUTING.md`, `docs/`, `CLAUDE.md`)에서 배치와 이름을 정한 문장을 찾고, 각각에 그렇게 정한 이유가 함께 적혀 있는지 본다. 규약은 판정보다 앞선다 — `common.md` 판정 6.
3. 현재 저장소의 디렉토리 구조와 파일 목록을 확인한다. 소스 디렉토리의 파일 수, 폴더 이름, 파일 이름을 센다. 무엇을 세지 않는지는 아래 Edge Cases에 있다.
4. 기준과 어긋나는 항목을 찾는다. 항목마다 **파일 또는 폴더 경로**, **어느 판정과 어긋나는지**, **무엇으로 고칠 수 있는지**를 적는다. 이유가 적힌 규약이 정한 것은 여기 넣지 않는다.
5. 이유 없이 이름만 정한 규약이 판정과 어긋나면 규약 수정 제안으로 따로 모은다. 코드만 고치면 문서와 코드가 갈라지므로 어긋난 항목과 처분이 다르다.
6. 참조 파일에 기준이 없어 판단하지 못한 것을 따로 모은다. 어긋난 항목과 섞지 않는다.
7. 전부 나열한 뒤, 적용 범위를 사용자와 정한다 — 새로 쓰는 코드에만 적용할지, 기존 코드까지 고칠지.
8. 사용자가 고른 것만 고친다.

어긋난 항목이 없으면 없다고 말한다.

### 점검 결과 형식

이 형식으로 낸다.

```markdown
## 구조 점검 — <저장소 이름>

**확인한 범위**

| 패키지 | 소스 디렉토리 | 파일 | 폴더 |
|---|---|---|---|
| <이름> | <경로> | <N>개 | <M>개 |

세지 않은 것: <경로>와 뺀 이유. 테스트를 포함했으면 그 개수도 적는다.

### 어긋난 항목

1. `<파일 또는 폴더 경로>` — <판정 번호와 제목>
   - 지금: <현재 상태>
   - 고침: <무엇으로 바꾸나. 참조 파일에 대안이 없으면 그렇다고 적고, 추론으로 채운 것은 추론이라고 표시한다>

2. `<경로>` — ...

### 규약과 함께 고칠 것

3. `<경로>` — <판정 번호와 제목>
   - 규약: <문서 경로와 그 문서가 정한 것>. 그렇게 정한 이유는 적혀 있지 않다.
   - 제안: <문서의 어느 부분을 어떻게 고치나>. 따라 바뀌는 코드 <N>개.

### 확인했고 문제없는 것

- <판정 번호와 제목>: <왜 문제없는지 한 줄. 규약을 근거로 넘어간 것은 그 문서의 위치를 적는다>

### 판정이 없는 것

- `<경로>` — <무엇을 판단하려 했나>. 참조 파일에 기준이 없다.

### 정할 것

고칠 항목의 번호와, 새로 쓰는 코드에만 적용할지 기존 코드까지 고칠지 알려주세요.
```

번호는 어긋난 항목이 여러 묶음이어도 다시 시작하지 않고 이어서 매긴다.

## Edge Cases

| 상황 | 어떻게 하나 |
|---|---|
| 벤더와 생성 코드가 섞여 있다 | `node_modules/`, `.venv/`, `vendor/`, `dist/`, `build/`는 세지 않는다. 그 밖에 무엇이 생성물인지는 저장소에서 찾는다 — 린터 설정의 제외 목록(`biome.json`의 `includes`, `.eslintignore`)과 `package.json`의 생성 스크립트가 근거다. CLI가 만들어 넣는 파일도 생성물이다 |
| 테스트 파일이 소스 옆에 있다 | 세되 몇 개인지 따로 밝힌다. 규모 구간 경계에 걸리면 포함한 경우와 뺀 경우의 결론을 함께 적는다 |
| 패키지가 여럿이다 | 판정은 패키지 하나에 적용된다. 패키지마다 따로 세고 따로 보고한다. workspace 설정 파일이 있다고 여럿인 것이 아니다 — `pnpm-workspace.yaml`의 `packages:` 항목과 실제 `package.json` 개수로 판정한다 |
| 소스 디렉토리가 불분명하다 | `src/`가 없으면 무엇을 소스로 볼지 사용자에게 먼저 확인한다. `src/`가 있어도 그 밖에 소스가 있으면(`tests/`, `scripts/`, 루트 설정) 무엇을 범위에 넣고 뺐는지 밝힌다 |
