# Deep Verify

산출물을 만든 컨텍스트는 그 산출물의 결함을 잘 보지 못한다. 완료 선언 직전에 "다른 사람의 눈"을 흉내 내는 별도 패스를 강제해, "될 것 같다"로 끝나는 완료 보고를 막는다.

## 적용 경계

- **발동**: 비자명한 산출물의 완료 보고 직전 - 조사 보고서, 문서 재구성, 설계안, 하네스 없는 레포의 코딩, cron·헤드리스 파이프라인.
- **양보**: oh-my-harness 활성 프로젝트의 정식 개발 플로우. completion-drift-guard·code-review가 이미 커버하므로 중복 실행하지 않는다.
- **스킵**: 단답·한 줄 수정·사실 조회처럼 검증 패스가 산출물보다 비싼 작업.

## 공통 프로토콜 (순서 고정)

1. **스펙 재대조**: 요구사항 원문을 처음부터 다시 읽고 산출물과 항목별 대조표를 만든다. 기억으로 하지 않는다.
2. **자기 반박**: "이 결과가 틀렸다면 어디가 틀렸겠는가" 가설을 3개 이상 세우고 각각 실제로 점검한다.
3. **증거 수집**: 점검마다 실행 출력·인용·대조 결과를 남긴다. 증거는 이번 검증에서 새로 실행한 출력만 인정한다(과거 실행 결과 재인용은 증거가 아니다). 점검 불가 항목은 한계로 명시한다.
4. **적대 리뷰** (규모 있는 산출물 한정): 아래 "산출물 적대 리뷰" 블록으로 별도 컨텍스트(서브에이전트)의 리뷰를 받는다. 작성한 컨텍스트가 스스로 채점하는 한계를 컨텍스트 분리로 보완한다.
5. **판정**: 결함 0개면 가설을 1개 추가해 재점검 후 종료한다. 첫 패스 무결함은 드물다.

## 도메인 스윕

### 코딩 (경량 - 정식 플로우는 oh-my-harness 소관)
- 엣지: 빈 입력 / 경계값 / 동시 실행 / 재실행 멱등성 / 실패 경로 / 자원 수명(누수)
- 스펙의 수량 표현("미만"·"이하"·"초과"·"까지")과 코드의 비교 연산자를 짝지어 확인
- docstring·주석·문서의 주장도 스펙이다: 코드가 그 주장을 실제로 이행하는지 검증
- 테스트는 수정 전 실패를 먼저 확인(fail-first)한 뒤 수정 후 통과를 보인다

### 조사·리서치
- 모든 주장에 출처 표기. 출처 없는 문장은 삭제하거나 [추정] 라벨
- 소스 간 상충을 능동적으로 찾는다: 공식성·최신성으로 서열을 정하고 채택 근거를 기록
- 기본값·묵시 동작의 변화는 명시적 API 변화보다 위험하다: 조용히 동작이 달라지는 지점을 별도로 찾는다
- "찾지 못함"과 "없음"을 구분해 표기

### 문서·글쓰기
- 산출물의 모든 고유명사·수치·날짜를 원문에서 재확인. 원문에 없는 사실 창작 금지
- 상충 항목마다 해소 규칙을 조건 분기까지 기계적으로 적용하고 근거를 기록
- 형식 계약(구성·순서·분량·어조)을 제출 직전 항목별 체크

### 무인 자동화 (스윕 + 설계 규약)
- **무인화 전제**: 테스트·린트·스키마·diff 범위 중 최소 하나로 성공을 자동 판별할 수 있어야 한다. 하나도 없으면 그 작업은 무인화하지 않는다.
- **설계 규약 5종**: 중복 실행 잠금 / 멱등 기록(고유키 upsert) / 재시도 상한+백오프 / 부수효과 완료 후 상태 커밋 / dead man's switch(무소식 경보)
- 스윕: 겹침 실행 / 부분 실패 후 재실행 / 외부 API 오류·빈 응답·rate limit / 프로세스 중간 사망 / 비밀값의 로그·출력 노출 / exit code 실패 전파(성공 위장 exit 0 금지)
- 침묵 실패 경로가 하나라도 남으면 미완성이다

## 완료 보고 계약

검증을 마친 완료 보고는 다음을 갖춘다: 1) 산출 요약 2) 통과 조건별 실제 증거 3) 검증하지 못한 것과 이유 4) 남은 리스크. "될 것 같다"류 표현이 남아 있으면 그 항목은 미완성으로 간주한다.

## 프롬프트 블록 (위임·새 세션용 복붙)

작업을 서브에이전트·다른 세션에 위임할 때 지시문에 부착한다.

**착수 계획 4줄** (지시문 앞):
```
실행 전에 4줄 계획을 먼저 제시하라: 목표 / 단계(산출물 명시) / 단계별 통과 조건(자동 판별 수단) / 완료 기준. 계획 없이 실행부터 하지 마라.
```

**완료 보고 계약** (지시문 말미):
```
완료 보고 형식: 1) 요약 2) 통과 조건별 실제 실행 출력 3) 검증 못 한 것과 이유 4) 남은 리스크. "될 것 같다"류 표현이 나오면 그 항목은 미완성으로 간주한다.
```

**산출물 적대 리뷰** (별도 컨텍스트에 — 공통 프로토콜 4단계와 위임 검수 겸용):
```
너는 이 산출물의 작성자가 아니다. 원 요구사항과 산출물만 보고 갭을 찾아라: 요구 위반, 누락, 근거 없는 주장, 원문에 없는 사실. correctness와 명시 요구에 영향 있는 갭만 보고하고, 스타일 취향은 제외하라. 갭이 없으면 억지로 만들지 말고, 무엇을 어떻게 점검했는지와 함께 "갭 없음"으로 보고하라.
```

**막힘 재시작** (같은 문제 2회 초과 실패 시, /clear 후):
```
다음 문제를 처음부터 접근하라. 증상: ... / 실패한 접근과 각각의 이유: ... / 검증 방법: ...
이전 시도를 답습하지 말고 원인 가설 3개를 세워 가장 유력한 것부터 검증하라.
```
