# reflect

지침이 있었는데 어긋난 동작을, 그것을 만든 컨텍스트 밖에서 다시 본다. 변명·합리화가 아니라 *증거로 확정한 근본원인*을 짚고, 그 원인이 곧 개선을 보낼 목적지를 정한다. 판정은 "내가 왜 틀렸나"(추궁→합리화 유발)가 아니라 **"이 산출물이 이 지침 조항을 지켰나"**(제3자 평가)로 한다.

## 적용 경계

- **발동**: 사용자가 지침 위반을 지적할 때(트리거 문구는 description이 SSOT). 단순 구현 의도 질문 "왜 이렇게 했어?"는 위반이 아니면 대상 아님.
- **스킵**: 지침 근거 없는 취향 차이(반성 아님, 조정) / 결과만 필요한 단순 재작업 / 테스트·코드리뷰로 잡는 코드 버그 / 완료 전 예방 검증(위반 후 진단이 아니라 사전 게이트).

## 진단 강도 (하이브리드)

- 평가형 프레이밍 + 증거 grounding은 **항상**.
- **별도 서브에이전트 격리 진단은 반복·구조적 사안에만** — 같은 위반 재발, 여러 지침이 얽힘, 원인이 자산 구조로 의심될 때. 실패 세션 컨텍스트가 자기합리화를 유발하므로 증거만 넘겨 fresh context에서 판정.
- 사소·단발 위반은 인라인. 단발이라도 아래 *증거 게이트*는 똑같이 적용해 합리화를 막는다.

## 흐름

증거 수집 → 진단(판정 + 원인 확정) → **로그 기록** → 처방 제안 → 승인 게이트 → 반영·이슈. 로그는 승인 게이트보다 *먼저*라 사용자가 반영을 거절해도 기록은 남는다.

### 1. 증거 수집 — grounding
사용자 지적(`$ARGUMENTS` 또는 대화)에서 출발한다. 기억에 의존하지 않고 두 가지를 실제 인용한다.
- **위반 지침 원문** — 어느 스킬/`CLAUDE.md` 조항/메모리인지 파일·위치까지. `Grep`으로 실제 문구를 찾아 인용.
- **실제 산출물** — 무엇을 했는지 diff·명령·출력·메시지 그대로.

### 2. 진단 — 평가형 + 증거로 원인 확정

먼저 판정: **"이 산출물이 인용한 조항을 지켰나?"**
- **지켰는데 결과가 의도와 다름** → 위반 아님. 원인은 지침이 의도를 덜 담은 것 → *의도 구체화*(지침 보강 제안). 결함으로 몰지 않는다.
- **안 지켰음** → 아래 표에서 원인을 *증거로* 확정한다. 원인은 서로 배타 — 증거가 가리키는 하나로.

| 근본원인 | 확정 증거 (없으면 그 원인 아님) | 처방 → 목적지 |
|---|---|---|
| **부재** | 관련 위치를 `Grep`했으나 규칙이 실제로 없음 | 룰 신설(reflect가 저작) → scope로 tier 결정 후 `CLAUDE.md`·메모리 |
| **오류·모호** | 규칙 원문 인용 + 문구대로 따랐을 때 어긋나는 지점 | 리라이트 → ai-doc-improver |
| **미도달** | 규칙이 이 세션 컨텍스트에 *있었음*을 인용 + 안 닿은 이유(긴 문서 내 위치 / 세션 거리) | 문서 내 위치면 재배치→ai-doc-improver, 메모리 배치면→memory-manager, 강제가 필요하면 hook 승격→update-config |
| **충돌** | 상충하는 두 규칙 원문을 나란히 인용 | 우선순위 명시 → 해당 문서(ai-doc-improver) |
| **행동 패턴** | 지침엔 결함 없음 확인 + 실행 습성(예: 조기 가정 후 미교정) 시점 특정 | 절차 체크 추가 / 반복되면 hook 승격→update-config |

**confabulation 반려**: "깜빡했다·못 봤다·오해했다"는 원인이 아니라 *증상*이다. '미도달'은 규칙이 실제 컨텍스트에 있었음을 인용해야, '오류·모호'는 오해를 부른 문구를 인용해야 성립한다. 증거를 못 대면 반려하고 판정으로 되돌아간다.

**처리 시점(원인과 별개 축)**: 각 위반은 `지금 delta 반영` 또는 `별도 세션 gh issue`(이번 세션서 못 고칠 구조 개선) 중 하나로 태그.

### 3. 로그 기록 (승인 게이트 전, 항상)
`~/.claude/reflections/YYYY-MM-DD-<slug>.md` 작성. 반영 여부와 무관하게 항상 남긴다. frontmatter는 아래 *로그 스키마*.

### 4. 처방 제안
2단계 표의 목적지대로 개선안을 만든다. 다른 스킬이 owner면 핸드오프(ai-doc-improver·memory-manager·update-config), `gh issue`면 제목·본문·완료조건 + **로그 slug를 본문에 임베드**(별도 세션이 맥락 복원). 원인이 복합이면 원인별로 각각.

### 5. 승인 게이트 → 반영·이슈
- **delta로만** — 자산 전면 재작성 금지(context collapse). 최소 변경.
- **scope 태그** — 개선안마다 `repo`만 / 이 `task`만 / `global` 명시. 룰 신설은 이 태그로 tier 결정(global→`~/.claude/CLAUDE.md`, repo→프로젝트 메모리).
- **승인 후 실행** — confirm 전엔 미리보기만. confirm 후 문서 반영 or `gh issue create` 실행. cwd가 repo 아니면 `~/.claude`(repo일 때) 또는 프로젝트 문서로 폴백.
- **status 갱신** — 로그 frontmatter를 `routed`→`applied`|`rejected`로.

## Tone 규약 — 변명 없이 사실 그대로

진단 self-review 잣대. 위반 발견 시 다듬고 재점검.

| 잣대 | Positive | Negative |
|---|---|---|
| 지침 인용 | `~/.claude/CLAUDE.md` "커밋 전 확인" 조항 원문 | "확인하랬는데" |
| 산출물 인용 | 실제 diff·명령·출력 그대로 | "그냥 해버림" |
| 원인 = 증거 | "규칙이 300줄 문서 210행에 있어 미도달(위치 인용)" | "깜빡함" |
| 책임 귀속 회피 | "지침이 문서 중간에 묻혀 안 읽힘" | "내가 부주의했음" |
| 정당화 회피 | "이 조항 미준수" | "그럴 만한 사정이 있었음" |

## 로그 스키마·lifecycle
```
---
date: YYYY-MM-DD
cause: absent | wrong | unreached | conflict | behavior | intent-underspecified
scope: repo | task | global
disposition: now | separate-session
status: logged | routed | applied | rejected
---
```
본문: 위반 지침 인용 / 실제 산출물 / 진단(평가형) / 처방·목적지.
- **재발 탐지**: `grep "cause:" ~/.claude/reflections/*.md`로 같은 원인 누적을 센다 — 반복되면 hook 승격(프롬프트 준수율보다 결정적)의 근거.
- **stale**: `date`+`status`로 계산. 30일 지난 `logged`|`routed`는 재검토, 90일은 아카이브 후보로 *보고*(자동 삭제 금지).

## Edge Cases
| 상황 | 대응 |
|---|---|
| 지적이 한 줄 | 증거 수집에서 위반 지침·산출물을 되물어 보강 |
| 규칙을 못 찾음 | `Grep`으로 *실제 부재*면 '부재', 긴 문서에 *있는데 안 읽혔으면* '미도달' — 처방이 반대(신설 vs 재배치)라 반드시 구분 |
| hook 승격 처방 | 배선은 update-config 영역 + outward 변경 → 반드시 승인 후 |
| 사용자가 진단에 동의 안 함 | 반증을 증거로 재수집해 재판정(자기일관성 고집 금지) |

## Output
- 증거로 grounding한 진단 보고(위반 지침·산출물 인용 + 확정 원인)가 실 산출물.
- `~/.claude/reflections/…md` 로그 + 원인별 처방 제안 + (승인 후) 반영·이슈 내역.
- 터미널에 근본원인·목적지 한 줄 요약 + 로그 경로.
