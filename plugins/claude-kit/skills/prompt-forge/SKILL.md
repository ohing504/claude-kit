# prompt-forge

대충 던진 요청 → **반응형 인터뷰로 의도 정밀화** → 다른 실행에 붙여넣을 **의도 명세(intent spec)**. 산출물은 프롬프트 형식이지만, 문구를 다듬는 게 아니라 *무엇을 시키려는지*를 인터뷰로 뽑아내는 게 본질이다 — 원샷·반복 실행(loop)일수록 모델이 의도를 추측할 여지를 인터뷰가 미리 없앤다.

## 흐름

인터뷰 → 최종 프롬프트 → 출력·저장. **인터뷰를 건너뛰고 바로 프롬프트를 쓰지 않는다** — 요청이 이미 상세해도 반응형 질문 1회는 의도를 더 정밀화한다.

1. **rough ask 수집** — `$ARGUMENTS`가 있으면 그것을 초기 요청으로 삼고, 없으면 사용자 발화에서 받는다.
2. **타깃 식별** — 이 프롬프트를 *어디에 쓸지*가 최종 프롬프트의 구조·강조점을 바꾼다. 요청에서 추론되면 그대로, 불명확하면 첫 질문으로 확정한다. 타깃별 델타는 아래 "타깃별 델타" 참조.
3. **반응형 인터뷰** — 한 번에 1-2개씩. 답을 분석해 다음 질문을 고도화(추상→구체). *의도·시나리오·크리티컬 결정*만 묻고 구현 디테일은 안 묻는다(아래 "무엇을 묻나" 참조). 의도가 정밀해지면 멈춘다.
4. **최종 프롬프트 작성** — 아래 "프롬프트 구조"대로. 모호어 금지, 명시 단계, 성공 기준 포함. 인터뷰에서 못 채운 칸은 *가정으로 채우고 그 가정을 따로 명시*한다(추측을 프롬프트에 몰래 심지 않는다).
5. **출력 + 검토 요약** — 길이로 나눈다. **터미널을 프롬프트 본문으로 꽉 채우지 않는 게 원칙** — 길면 복사가 오히려 불편하다. 어느 경우든 **검토 요약**을 함께 낸다: 프롬프트가 시키는 것 1줄 + 인터뷰에서 확정·가정한 **크리티컬 결정 3–5개**. 사용자는 이 요약만으로 의도 일치를 확인(OK/수정)하고 본문은 실행 측이 읽는다 — 긴 프롬프트를 통독해야 검토되는 부담을 없앤다.
   - **짧으면**(한 화면 이내, 대략 20줄 이하): 최종 프롬프트를 코드블록으로 인라인 출력(복붙용) + 검토 요약. (재사용 원하면 파일 저장도 제안)
   - **길면**(한 화면 초과): 전체를 터미널에 쏟지 않는다. `prompts/` 폴더(없으면 생성)에 내용 드러나는 서술형 이름의 `.md`로 저장하고, 인라인엔 다음 세션에 그대로 복붙할 **짧은 핸드오프 지시문 1-2줄**만 출력한다 + 검토 요약.
     - 핸드오프 예: `` `prompts/<name>.md` 파일을 읽고 그 안의 프롬프트를 그대로 실행해줘 `` — 다음 세션의 순정 Claude가 스킬 없이도 이해하게 자급자족으로.
     - 임시 맥락(일회성 문서·해결되면 쓸모없어질 내용)이 든 프롬프트면 저장 시 그 사실을 알린다 — 재사용 자산이 아니라 쓰고 지우는 파일이다.

## 무엇을 묻나 (인터뷰 잣대)

한 번에 묶음 질문을 다 던지지 않는다. 답에 반응하는 질문이 인터뷰 품질을 만든다 — 질문 수가 아니다.

**묻는다 (의도 영역):**
- 목적 — 이 작업으로 궁극에 뭘 얻나. 성공한 결과는 어떤 모습인가(성공 기준).
- 시나리오 — 입력은 무엇이고 출력은 어디에 쓰이나. 누가·언제 실행하나.
- 크리티컬 결정 — 되돌리기 어렵거나 값이 큰 선택(범위 경계, 보안·데이터 취급, 반드시 지킬 제약, 절대 하면 안 되는 것).
- 실패 모드 — 특히 걱정되는 오작동·엣지케이스가 있나 (ultracode 타깃에서 중요).

**안 묻는다 (구현 영역 — 프롬프트가 알아서 열어두거나 실행 측 자율):**
- 코드 표현·변수명·라이브러리 선택·N 값 같은 세부, 문구 다듬기.
- 답이 모호·일반적이면 그 자리에서 파고든다("빠르게"가 뭘 의미하나 — 지연? 처리량? 체감?).

**질문 형태:** 열린 의도 파악은 자유 서술 질문으로. 갈래가 명확한 선택(타깃 확정, 크리티컬 포크)은 `AskUserQuestion` 옵션 카드로 — 추천 옵션을 맨 앞에 두고 근거 동반, description만으로 결정 가능하게.

## 타깃별 델타

식별한 타깃에 따라 최종 프롬프트에 아래를 더한다. 하나만 적용된다.

- **ultracode (복잡·견고 작업)** — 견고성을 프롬프트에 명시적으로 심는다: 다뤄야 할 엣지케이스·실패 모드 열거, 자체 검증/애드버세리얼 체크 요구("작업 후 스스로 반박·검증하라"), 되돌리기 어려운 동작 전 확인 게이트, 검증 증거(테스트·실행 결과) 요구. 안정성이 속도보다 우선임을 못박는다.
- **Fable 원샷 (단일 패스 정밀)** — 되물음 없는 한 방 실행 전제: 모든 맥락을 프롬프트 앞에 몰아넣고(뒤늦은 참조 금지), 출력 계약을 엄격히 고정(형식·길이·포함/제외 항목 명시), 모호할 때 되묻지 말고 명시한 가정으로 진행하라고 지시. 애매함을 남기지 않는 게 핵심.
- **일반 에이전트/세션** — 위 둘의 중간. 구조화·성공 기준·제약은 유지하되 상호작용 여지를 열어둔다(막히면 되물어도 됨).
- **loop 시드 (반복 실행 오케스트레이션)** — 사람이 매 턴 킥오프하지 않고 런타임이 자동 반복하는 실행이 매 회 읽는 명세. 단발 세션과 달리 목표를 대화가 아니라 *바깥 파일*에 반복 재현되게 고정한다: 목표 + **완료 정의(definition-of-done)** + **검증자**(테스트·스키마·diff 등 성공을 자동 판별할 수단 — 없으면 loop이 오답을 성공으로 오판) + **종료조건**(언제 멈추나·최대 반복). 세션 의존 표현·모호어를 없애 매 반복 같은 기준으로 실행되게 한다.

## 프롬프트 구조

최종 프롬프트는 아래 골격을 채운다. 섹션 라벨은 대상에 맞게 자연스럽게 조정하되 순서(역할→맥락→목표→제약→출력)는 유지한다 — 맥락을 앞에, 출력 계약을 뒤에 두는 게 실행 정확도를 높인다.

```
[역할] 무엇으로서 작업하는가 (필요 시)
[맥락] 배경·입력·전제. Fable 원샷이면 여기에 모든 정보를 몰아넣는다.
[목표] 달성할 것 + 성공 기준(성공한 결과의 구체적 모습)
[단계] 모호어 없이 명시적 번호 단계 (필요한 작업만, 억지 분해 금지)
[제약] 반드시 지킬 것 / 절대 하면 안 되는 것 / 크리티컬 결정
[출력] 형식·길이·포함·제외. 엄격히.
[타깃 델타] 위 "타깃별 델타"에서 해당분
```

원칙: **고밀도**(실행에 필요한 명시는 유지하되 의례적 문구·중복은 뺀다 — 정밀함과 장황함은 다르다). **모호어 제거**("적절히"·"알아서"·"필요에 따라"는 명시 단계·기준으로 대체). **긍정형 지시 우선**(금지 나열보다 "무엇을 하라"). 근거 없는 대문자 명령(ALWAYS/NEVER) 대신 *이유 동반 서술*.

## Edge Cases

- **요청이 이미 상세함** — 인터뷰를 통째 생략하지 않는다. 남은 크리티컬 결정·성공 기준만 짚는 반응형 질문 1회로 축소.
- **사용자가 인터뷰 스킵을 요구** — 크리티컬 결정 1개만 확인하고, 나머지는 가정으로 채워 최종 프롬프트와 함께 가정을 명시한다(되물음 대신 명시적 가정).
- **타깃이 셋 중 어디에도 안 맞음** — 일반 에이전트 델타를 기본으로 쓰되, 그 실행 환경 고유의 제약(모델·도구·형식)을 인터뷰로 물어 반영.
- **기존 프롬프트를 개선 출발점으로 받음** — 새로 만들지 않고 그 프롬프트를 읽어 의도를 인터뷰로 보강한 뒤 재작성한다.
- **타깃이 loop 시드** — 산출은 길이와 무관하게 `prompts/`(또는 사용자 지정 goal 경로) 파일로 저장한다. loop이 매 실행 읽을 대상이라 인라인 복붙이 아니라 파일이 기본이다.

## 안 하는 것 (책임 경계)

- **프롬프트를 세션 내에서 실행하지 않는다.** 이 스킬의 산출물은 최종 프롬프트 텍스트(+ 선택적 파일)까지다. 실행은 사용자가 대상 세션·모델에 붙여넣어 한다.
- **없는 사실을 창작하지 않는다.** 인터뷰로 얻지 못한 정보는 가정으로 명시하고, 프롬프트 본문에 확인 안 된 사실을 심지 않는다.
- **문서 다이어트가 아니다.** 이미 있는 프롬프트·문서를 다듬는 건 `ai-doc-improver` 소관. 이 스킬은 의도에서 프롬프트를 새로 만든다.
